# problem

Stowarzyszenie prowadzi serwis redakcyjny i organizuje biegi. Biegacze chcą w tym samym miejscu sprawdzić wyniki, rankingi i własne konto.

Strony redakcyjne dobrze obsługuje WordPress, ale część dla biegaczy to aplikacja: listy z sortowaniem, wyszukiwarka, logowanie, generowanie plików. [Dopisz, co było punktem wyjścia i ograniczeniem.]

# architektura

WordPress

Motyw PHP na Tailwindzie: strona główna, artykuły, partnerzy, strony biegów.

->

SPA w Preact

Wszystkie strony dla biegaczy, osadzone we wpisach shortcodem. Vite, TypeScript, własny router.

->

API w Laravelu

app.itmbw.pl: publiczne JSON API i wewnętrzny CMS w React do zarządzania danymi.

Strona biegacza to zwykły wpis WordPressa. Router aplikacji wybiera widok po adresie, a logowanie działa przez sesję współdzieloną między domeną i subdomeną API.

# kluczowe decyzje

  1. 01 Aplikacja wewnątrz WordPressa, nie obokRedakcja zostaje przy znanym edytorze, a biegacz nie opuszcza serwisu. Adresy aplikacji pokrywają się z adresami wpisów.
  2. 02 API jako kontraktDokumentacja OpenAPI powstaje z kodu, a test pilnuje, żeby żadna trasa nie została bez opisu.
  3. 03 Cache z natychmiastowym czyszczeniemOdpowiedzi API i gotowe strony są cache’owane, a każda edycja w CMS-ie od razu unieważnia oba poziomy.
  4. 04 Dane wydarzeń w rękach redakcjiDane strukturalne biegów (SportsEvent) uzupełnia się w edytorze strony — nowa edycja nie wymaga wdrożenia.
