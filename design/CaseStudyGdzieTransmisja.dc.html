# problem

Informacje o tym, gdzie obejrzeć mecz, są rozrzucone po wielu źródłach. Kibic chce jednej odpowiedzi: kanał, godzina, miejsce.

Po stronie kodu to kilka aplikacji naraz — strona dla kibiców, panel redakcji, API i import danych — które muszą posługiwać się tymi samymi typami. [Dopisz, skąd wziął się pomysł i kto za nim stoi.]

# architektura

@gt/data

Scrapery i import transmisji z zewnętrznych źródeł.

->

@gt/api

NestJS, Drizzle, Zod i PostgreSQL. Autoryzacja JWT, pliki, zadania cron.

->

@gt/web

Publiczna strona w Next.js: transmisje, miejscówki, ligi.

@gt/admin

Panel redakcji na react-admin i Vite.

Całość spina pakiet @gt/shared: typy, enumy i narzędzia używane przez wszystkie aplikacje. Monorepo działa na pnpm workspaces i Turborepo.

# kluczowe decyzje

  1. 01 Typy z jednego źródłaSchemat bazy w Drizzle daje schematy Zod, te dają OpenAPI, a z niego generują się typy i enum tras dla frontendów.
  2. 02 Adresy strony jako typTypy ścieżek powstają ze struktury katalogów Next.js, razem z tłumaczeniami tras na polski i angielski.
  3. 03 Komponent to sam widokPlik komponentu zawiera tylko JSX. Logika trafia do jednego hooka obok, a strona tylko pobiera dane i renderuje.
  4. 04 Jedno repo, osobne wdrożeniaStrona i panel wdrażają się na Vercelu, API na Railway. Migracje bazy API uruchamia samo przy starcie.
